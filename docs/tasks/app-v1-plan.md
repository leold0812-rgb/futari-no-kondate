## 進め方

- Gateごとにブランチ → PR → CI（lint / typecheck / unit / build、DB pgTAP、Auth統合、E2E）→ Codexレビュー（`codex review --base main`）→ Critical解消 → マージ。
- MacにDockerがないため、Supabaseを使うテスト（pgTAP・統合・E2E）はGitHub Actionsのローカル Supabase で実行する。hosted Supabaseには接続しない。
- hosted Development / Productionの操作（Supabaseのlogin・DB password・secret key・Auth設定・Vercelの秘密値）は、Claudeが資格情報を扱えないため、`docs/runbooks/`の手順書としてユーザーへ渡す。

## 判断ログ（Gate 1.4以降）

番号は下の「判断ログ」（1〜、Gate 1.3のPRに4〜5あり）の続き。

6. PINは`scrypt(HMAC-SHA256(PIN_PEPPER, PIN))`で保存し、pepperを新しいサーバー環境変数`PIN_PEPPER`にする / 6桁PINはDBのハッシュだけ漏れると総当たりできるため。pepperはDBと別の場所（Vercel）に置く。
7. ロックはアカウント単位で連続5回失敗→15分・30分・60分（上限60分）、送信元単位で1時間20回 / 総当たり耐性（6桁で数年以上）を保ちつつ、第三者のわざとの失敗で2人が長時間ログインできなくなる影響を1時間までに抑える。
8. PINは6〜12桁の数字で、同じ数字だけ・連番を設定時に拒否する / 仕様「6桁以上」と推測されやすいPINの排除。
9. PINの設定・再設定は管理スクリプト（`scripts/auth/set-pin.mts`、端末で非表示入力）で行い、アプリ内のPIN変更画面は作らない / 本人確認なしの自己設定は安全に作れず、2人専用なので管理者操作で足りる。ロック解除も同じコマンド。
10. ログイン画面では未ログインでも2人の表示名だけを表示する（サーバーがsecret keyで読む） / 仕様の「ユーザー選択」に必要。表示名以外は出さない。
11. ログアウトは「この端末だけ」（`signOut({ scope: "local" })`）とし、設定画面（記録タブ右上）に置く / 相手や他端末のログインを巻き込まないため。
12. E2EはPlaywright（devDependency `@playwright/test` 1.63.0、完全固定）でCIのローカルSupabaseに対して実行し、画面のスクリーンショットをartifactに残す / MacにDockerが無く、画面の動作確認をCIで行う必要があるため。bundleへの影響なし。
13. PRのマージは分類器に拒否されたため、Gateごとのブランチを積み重ね（stacked PR）、最後にユーザーが順にマージする / ユーザー承認なしのマージはできないため。
14. `.env.example`（値は空）はClaudeの権限設定で編集できないため、`PIN_PEPPER=`の行追加はユーザー作業として残す。
15. PIN照合の対象はprofileとPIN登録のある利用者だけにし、それ以外のIDでは試行行を作らず照合もしない。1日以上前の送信元記録は自動削除 / Codexレビュー（PR #7 Critical）の未認証DoS指摘への対応。

16. レシピの手順は「1行に1つ」のテキストエリア、材料の分量は「200g」「大さじ1と1/2」「少々」を1つの欄で入力し、保存時に数量と単位へ分ける / 仕事後の入力量を減らすため（UIは行ごとの材料＋まとめて貼り付け）。
17. 新しい材料は名前から保存目安の初期値（肉2日・魚1日・野菜5日・卵乳10日など、調味料・乾物は目安なし）を入れる / 「そろそろ使いたい」を購入日から算出するため。控えめな一般的目安で、材料ごとに変更できる（消費期限ではないと画面で示す）。
18. レシピ画像は private bucket に保存し、期限付き署名URLで表示する（next/imageは使わない）。ブラウザで長辺1600pxのJPEGへ縮小してから送る / 2人専用で配信量が小さく、URLが毎回変わるため最適化キャッシュが効かない。取り込み元サイトの画像は利用条件を確認できないため自動では複製しない（Gate 3で確認チェック付きの任意機能にする）。
19. レシピは論理削除（DB権限も物理削除なし）。評価は「また作りたい / ふつう / もう作らない」を本人だけが変更でき、相手の評価は表示のみ / 献立・履歴からの参照を壊さないため。仕様の「評価はユーザーごと」。
20. 新規依存 `zod` 4.6.5（完全固定）を追加 / レシピ入力とAI出力（Gate 3）のサーバー側検証を一か所で型と一致させるため。サーバー側だけで使い、client bundleへの影響はほぼない。
21. 栄養の食品成分表マスタと計算はGate 2bに分ける / 公式データの取り込み（ユーザーがダウンロードしたCSVを投入）を伴い、レシピ本体と分けてレビューしやすくするため。それまでは手入力の値だけを表示する（推測値は入れない）。

22. URL取り込みはJSON-LD（schema.org/Recipe）を最優先し、無い場合だけOpenAIを呼ぶ。OpenAIはSDKを使わずResponses APIをfetchで呼び、Structured Outputs（strict）＋zodで検証、`store: false` / 既定モデル `gpt-5-mini`（`OPENAI_IMPORT_MODEL`で変更可）/ 1 spaceあたり1日20回まで（上限の判定と記録はservice_role専用のDB関数で一体化し、サーバーがsessionで確かめた利用者とspaceを渡す。Codexレビュー Critical 2件への対応）/ 取り込み自体も1時間30回まで / 自動再試行なし / 30秒でタイムアウト / 利用記録はホスト名・方法・結果だけ / 多くのレシピサイトはAIなしで取り込め費用がかからない。AIに送るのは公開ページのタイトル・説明（500文字）・材料〜作り方の周辺（6000文字まで、コメント・関連記事・asideを除く）。材料の見出しが見つからないページはAIへ送らない。
23. SSRF対策は「形式検査（http(s)・既定ポート・認証情報なし・内部向けホスト名）＋接続時に全DNS解決結果を検査（rebinding対策）＋リダイレクト先ごとの再検査（3回まで）＋10秒・3MB・Content-Type制限」とし、Node標準のhttp(s)で実装した / 新規依存を増やさず、接続先IPを確実に検査するため。
24. 取り込み元の写真は、利用者が「利用条件で許可されている」と確認してチェックした場合だけサーバーが取得して保存する（既定はしない）。
25. 取り込みに失敗したURLは「URLだけ保存」（status URL_ONLY、献立候補には出ない）でき、詳細画面から「もう一度取り込む」でそのレシピを更新できる。内部向けURLなど不適切なURLは「URLだけ保存」も出さない。

26. 在庫はlot（購入単位）で持ち、数量0になったlotは消して履歴は監査表に残す。減算は互換単位のlotだけを古い順に行い、換算できない分は減らさず呼び出し元へ返す（推測で混ぜない） / AGENTS.mdの「互換単位だけ」と、どれから使ったかを説明できるようにするため。
27. 「そろそろ使いたい」は「残り日数が保存目安の3割（最低1日）以下」、保存目安を過ぎたものは「目安を過ぎています」と表示する（消費期限ではないと画面に明記） / 仕様の「購入日と保存目安から算出」。係数は運用で見直せるよう`lib/inventory/status.ts`に集約。
28a. 在庫表・監査表は利用者から読み取り専用にし、書き込みは内部関数に集約。利用者の入口は手入力の追加と手動補正だけで、監査の理由は関数が決める / Codexレビュー（PR #10 Critical）：直接書き込みで監査を通らない変更や「購入済み」「作った」の偽装ができたため。
28. 在庫の手入力は「材料名・分量（1欄）・購入日」だけ。材料のカテゴリと保存目安は別画面（材料の設定）でまとめて直す / 日々の入力量を減らすため。

29. 推薦アルゴリズム `weekly-v0.1`：仕様の点数（また作りたい+14/人、お気に入り+6/人、未調理+8、高タンパク+12、低カロリー+10、在庫で主な材料を賄える0〜10、使い回し0〜8（主な材料の共有1品につき4点）、30日以内に作った-10〜0、高コスト-8、特殊調味料-4）で貪欲に選ぶ。未調理は2品、候補15品以上かつ未調理3品以上なら3品。高コスト1品・同じ大分類5品までを守り、足りない時だけ緩めて理由を残す / 仕様の数値を「どう数えるか」を決定的に固定するため。
30. 計画できるのは今週と来週だけ。主菜はちょうど5品で確定（多ければ外す、少なければ候補の出し直し・レシピから追加） / 仕様「週5献立」。
31. 候補の判断（作る/スキップ）は押した瞬間に画面へ反映し、裏で保存する（失敗したら戻して理由を表示）。スワイプに加えボタン・矢印キーで操作でき、動きを減らす設定では傾き・移動を出さない / 仕事後にテンポよく選べることと、アクセシビリティの両立。
32. 設計案の`weekly_main_dishes`は作らず、`meal_sets`（主菜ごとの献立セット）に統合 / 主菜と副菜・汁物・作った状態を1か所で扱えるため。
33. 計画・推薦結果・判断・献立セットは利用者が直接書き込めない。判断も関数（計画行のロック・DRAFT・最新runを確認、版を進める）で行い、確定はDB側で「最新runの採用済みちょうど5品」だけを使う（Codexレビュー PR #11 Critical対応）。書き込みは関数内で自分のspaceかを確かめる`SECURITY DEFINER`関数だけ / `for update`のロックに必要な権限を利用者へ与えずに済み、状態の不正な書き換えを防ぐため。
